Human mode: The Fortis guide

Records#

Agent mode. Source of truth: the schema reference/schemas/diagnostic.schema.json, and LR 10.6, LR 10.8, LR 13 and LR 14 for the runtime records.

Every finding, runtime failure report, test result and observation the toolchain produces is a record first: a JSON object of a known kind, from which the text a person sees is rendered. Read the record, not the text.

Streams#

SituationWhat is written
standard output is a pipeone JSON object per line
standard output is a terminaltext rendered from the same record
--format json / --format textforces that rendering
a running program's records (failure reports, defects, logs, observation frames and events)standard error, same rule; the program's own output is standard output (LR 4.6)

Where each command writes, as the toolchain does today:

CommandStandard outputStandard error
fortis check, fortisc checkdiagnostic records—
fortis run, a native executablethe program's outputruntime records
fortis test (interpreter)the test-summary recordtest-result and other runtime records
fortisc test (VM)the test-summary recordtest-result and other runtime records, as fortis test writes them
fortis build, fortisc buildthe build recorddiagnostic records if the check fails
fortisc vmthe conformance format: === FILE, observed: … (output lines joined by |), trace: …, record: …—

A finding has one identity: fortis check, the daemon and the agent protocol produce byte-equal records for the same snapshot. fortis check (the reference checker) and fortisc check (the production checker) print records of this one schema, with the same codes at the same lines.

Diagnostic records#

Schema: reference/schemas/diagnostic.schema.json.

FieldTypeMeaning
codestringstable diagnostic code, E-XXX-NNN
classstringthe diagnostic class (table below)
rulestringthe normative rule the record enforces (LANG-, PROG- or PLAT- ID)
file, line, columnstring, integer, integerprimary location, the user's nearest responsible operation (1-based)
severityerror or warninga warning does not fail the check
statusviolated, unproved or unknowna proved violation, an inability to prove, an unknown trust boundary
messagestringone-line explanation
fieldsobjectthe class's mandatory fields
correctionobject, optional{kind, edits: [{file, line, column, end_line, end_column, replacement}]}, an applicable edit

unproved means the checker could not prove a bound, not that the program is wrong: supply the proof or use the checked alternative the message names (LR 6.3). A correction's kind is a short description of the edit (for example add the marker). A fix preserves behaviour, changes it or weakens a contract, but today's records do not carry that class, so judge it from the edit itself; the compiler never removes noalloc or a security requirement to make code compile, and an agent never applies an edit that weakens a claim.

Every code, its class, its rule and its correction pattern: codes.md.

Example: a violation#

The record for an assignment to an immutable binding (LR 5.1):

Fortis
// reject: E-NAM-002
pure func next(n: Int<0..9>) Int {
  let x = n
  x = 1                     // reject: E-NAM-002
  return x
}

test "next" {
  expect next(1) == 1
}
records
{"class": "Names and modules", "code": "E-NAM-002", "column": 3, "fields": {"candidates": ["let mut"], "name": "x"}, "file": "example.ft", "line": 4, "message": "`x` is immutable", "rule": "LANG-05-01", "severity": "error", "status": "violated"}

Example: an unproved bound#

An integer + the checker cannot prove in range is E-REF-002 with status unproved; proved_interval is what the checker established and required_range what the type needs (LR 6.4):

Fortis
// reject: E-REF-002
pure func sum(a: Int, b: Int) Int {
  return a + b              // reject: E-REF-002
}

test "sum" {
  expect sum(1, 2) == 3
}
records
{"class": "Refinement unproved", "code": "E-REF-002", "column": 12, "fields": {"proved_interval": "[-18446744073709551616, 18446744073709551614]", "required_range": "[-9223372036854775808, 9223372036854775807]", "widening_point": ""}, "file": "example.ft", "line": 3, "message": "`+` may overflow Int: operands [-9223372036854775808, 9223372036854775807] and [-9223372036854775808, 9223372036854775807] give [-18446744073709551616, 18446744073709551614]; use Int.add, or write the operator as the checked operation: `a + b or fail` (or `or recover`, `catch`)", "rule": "LANG-06-02", "severity": "error", "status": "unproved"}

Example: a record with a correction#

The text rendering lists the fields, then the correction's kind and each edit as file:line:column-end_line:end_column -> "replacement". A missing ownership marker (LR 7.5):

Fortis
// reject: E-OWN-001
class Note {
  export text: String
}

test "note" {
  let a = Note(text: "x")
  let b = a                 // reject: E-OWN-001
  expect b.text == "x"
}
output
example.ft:8:11: error E-OWN-001 [LANG-07-01] (Ownership, violated): `a` is an existing ownership-bearing place: write `copy a`, `alias a` or `move a`
    conflict: "marker required"
    loan_region: ""
    place: "a"
    spans: "a"
    correction: add the marker
      example.ft:8:11-8:11 -> "copy "

The edit inserts copy (a behaviour-preserving choice); move a or alias a are the other repairs the message names, chosen by what the code does with a afterwards (LR 7.5).

The backends do not yet agree on every field (D-57): the interpreter counts each property case as a test, native code writes evidence as a string, and a failure's origin has no line on any backend; fortis test and fortisc test write the same evidence, its line included. Match on kind, code, test and status.

Captured field values leave the process only through the Telemetry kit's pipeline; with no telemetry plan the task reporter writes a frame's schema, outcome class and duration but never a captured value (fields is empty), and FORTIS_TELEMETRY=permit-all is the explicit development plan that writes them unchanged (LR 15).

A failure's origin.file is never an absolute path, on any backend, so an executable does not depend on where it was built: a module of a package is named relative to the package's directory (src/pricing.ft), and a standalone module relative to the current directory when it lies below it, else by its file name.

A report of a declared error, as written by the interpreter and the native executable (LR 10.6):

json
{"annotations": [], "cause": [], "code": "demo.not_even", "kind": "runtime-failure", "message": "", "origin": {"file": "examples/02_outcomes.ft", "function": "half"}, "payload": {"value": "9"}, "reported_by": "report", "rule": "LANG-10-06"}

A frame and an event under FORTIS_TELEMETRY=permit-all (LR 13, LR 15):

json
{"fields": {"value": "5"}, "kind": "observation-event", "rule": "LANG-13-01", "schema": "Line"}
{"fields": {"items": "3", "total": "23"}, "function": "process", "kind": "observation-frame", "outcome": "success", "rule": "LANG-13-02", "schema": "OrderProcessing", "truncated": []}

A failed expect (LR 14):

json
{"case": "", "evidence": {"actual": "4", "expected": "== 5", "line": 4}, "kind": "test-result", "rule": "LANG-14-02", "status": "fail", "test": "deliberately wrong"}
