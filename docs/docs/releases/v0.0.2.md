# Fortis v0.0.2

Released 29 October 2026 by Pickering Technologies Ltd, under the MIT License ([LICENSE](../../LICENSE)).

v0.0.2 is the reading release. Fortis is optimised for reading, and v0.0.2 applies one principle to the language:
mark only what the reader can't already see. A marker earns its place when it says something surprising about the
line; if a declaration already says it, the marker is noise. Seventeen changes follow from that, listed below with
the Language Reference section that states each one.

Nothing you could write in v0.0.1 stops working. Every older form is still accepted, and `fortis fmt --write`
rewrites it into the newer one wherever the two mean the same ([Moving your code](#moving-your-code)). Everything in
v0.0.1's scope is still in scope; [v0.0.1](v0.0.1.md) describes it.

## What reads differently

The same program, written for v0.0.1:

```fortis
// illustrative: v0.0.1
import fortis.host { Host }

export try func main(args: List[String]) Void {
  let caps = Host.capabilities()
  let mut readings: List[Int<0..1000>] = List.of(12, 30, 18)
  editable readings.push(40)
  let total = Int.add(Int.mul(readings.count(), 100) or fail, 5) or fail
  caps.console.print("${readings.count()} readings, total ${total}")
}

test "the mean of four" {
  let readings: List[Int<0..1000>] = List.of(10, 20, 30, 40)
  expect (mean(readings) or fail) == 25
}
```

and for v0.0.2:

```fortis
// illustrative: v0.0.2
import fortis.host { Console }

try func main(console: Console) {
  let mut readings: List[Int<0..1000>] = List.of(12, 30, 18)
  readings.push(40)
  let total = readings.count() * 100 + 5 or fail
  log.info("summing ${readings.count()} readings")
  console.print("${readings.count()} readings, total ${total}")
}

test "the mean of four" {
  let readings: List[Int<0..1000>] = List.of(10, 20, 30, 40)
  expect mean(readings) == 25
}
```

`main` asks for the console it uses, and the runtime supplies it. `readings` is declared `let mut`, so the call that
changes it needs no marker of its own. The arithmetic is written as arithmetic, and one `or fail` covers the
expression. The test's call fails the test if it fails. What stays marked is what a reader could not otherwise
know: an argument a callee changes (`normalise(editable readings)`), a transfer (`move`), a copy or a loan in a
binding (`copy`, `alias`), and every failure decision outside tests.

## The changes

| | Change | Language Reference |
|---|---|---|
| R1 | The receiver of an `editable self` method, and a `fn mut` closure being called, are unmarked on a `let mut` binding: `readings.push(40)`, `bump()`. The call takes the same exclusive loan the marked form does, and is `E-OWN-001` on a place that cannot change. | LR 7.5, 7.6 |
| R2 | The same on an `editable` parameter, the method's own `editable self`, an `editable` or `move` capture, and a binding holding an exclusive loan. | LR 7.5 |
| R3 | `copy` and `alias` in bindings, capture-list markers, and `editable` and `move` on arguments stay: each says something the line does not. | LR 7.5, 8.3 |
| R4 | The entry `main` declares the capabilities it needs as parameters, supplied by type: `func main(console: Console, args: List[String])`. Names and order are yours; a type the runtime cannot supply is `E-NAM-005`, a type written twice `E-NAM-006`. Only the entry `main` receives capabilities, and it owns them. | LR 4.6, 11.6, 11.7 |
| R5 | `log.info`, `log.warn` and `log.error` write one `log` record to the diagnostic plane, never to standard output. They need no capability and have the `io` effect, like `report`. A failure is still recorded with `report e`. | LR 13, 11.6, 11.7 |
| R6 | A `Void` return type may be left out of any head, `cleanup` and `main` included. A function type keeps its result. | LR 8.1 |
| R7 | In `test` and `property` bodies a failing call fails the test: `or fail` is implied, and unproved `Int` arithmetic there is checked too. A call that `or`, `catch` or `match` consumes keeps its outcome. | LR 14, 6.4 |
| R8 | `export` is implied on the entry `main`, and `args` is declared only when it is used: `func main() { … }`. | LR 4.6 |
| R9 | A labelled argument puns: `wanted` for `wanted: wanted`, in a class's generated constructor and after a named argument. | LR 5.8, 9.2 |
| R10 | The formatter no longer prints a lambda's inferred `pure` and `noalloc` back, and an expression-bodied lambda may leave out its result type. | LR 8.2, 1.1 |
| R11 | `Map[String, V].get` takes its key as a `StringView`, so a lookup needs no `copy` or `String.from`. | LR 6.7 |
| R12 | Or-patterns in `match`: `A \| B => v`. The alternatives bind no names and take no guard (`E-MAT-003`). | LR 9.8 |
| R13 | `derive Default` gives `Name.default()` for a class whose fields all have defaults. | LR 6.10, 9.2 |
| R14 | Checked arithmetic as operators: an `Int` operation the checker cannot prove safe, under `or fail`, `or recover` or `catch`, is the checked operation, so `value * 10 + d or fail` replaces `Int.add(Int.mul(value, 10) or fail, d) or fail`. | LR 6.4, 6.3, 5.6 |
| R15 | An enum variant may be written bare where the expected type is that enum: `Error` for `Severity.Error`. A bare name that also names something else in scope must be qualified. | LR 9.7 |
| R16 | `return local` moves a local `let` or `let mut` binding without `move`. | LR 7.5 |
| R17 | `@ignorable` on a function declares that its result may be dropped, instead of `discard` at every caller. | LR 5.5, 11.8 |

The guide and the agent mode teach the new forms throughout, and mention each older form once. The [closed
decisions](../guide/appendix-b-decisions.md#the-reading-release-v002) give the reason for each change.

## Decisions for the owner's review

The owner reviewed the side-by-side examples and the reading pass and took every finding into v0.0.2. These are the
narrower decisions made while building it, each written into the Language Reference; any of them may be reversed
before the release.

- **The eight open questions** take the integrator's recommendation: a receiver is unmarked on an `editable`
  parameter (Q1), on the method's own `editable self` (Q2) and on an `editable` capture (Q5); `copy` and `alias` in
  bindings (Q3) and capture-list markers (Q4) stay; other functions take capabilities as ordinary parameters (Q6);
  `main` owns its capabilities and may wrap one in `Shared` (Q7); a failure is recorded with `report e`, and `log.*`
  is for what is not a failure (Q8).
- **Receivers.** A receiver is unmarked wherever `editable` could be written, including a binding that holds an
  exclusive loan and a `move` capture of a `fn mut`. An `editable self` call on a trivial value still needs a place
  that may change. A `from self` result is unmarked like any other.
- **`Void` and returns.** R6 covers every head, and a function type keeps its result. R16's "local" is a binding a
  `let` or `let mut` statement declares, not a destructuring, a `catch` binding, a pattern, a parameter or a capture.
- **The entry `main`.** Each parameter is plain `name: T`, with no mode and no default. Capability types are those
  of `fortis.host`. The entry is the entry module's `main` function, exported or not. `Host.capabilities()` is still
  accepted in a `main` with no capability parameter; in a `main` with one it is `E-EFF-010`, a second creation.
- **Logging.** A log statement has the `io` effect, so a `pure` function cannot log. Its record names the function
  that wrote it. `log` is not a keyword: where `log` names something, `log.info(...)` is an ordinary call.
- **Tests.** Only calls of `try` functions get the implied `or fail`; a function that returns an `Outcome` it built
  is not a failing call. A `let` that the body later consumes with `or`, `catch` or `match`, or annotates
  `Outcome[…]`, keeps the outcome.
- **Checked operators.** R14 covers `Int` only, since the other integer types have no checked family, and `>>` has
  none either. The region is the handler's left operand through the arithmetic operators and parentheses; it stops
  at calls, indexes, fields and comparisons. There is no `Outcome`-valued arithmetic, and `x += 1` stays
  proof-required. An unproved operator on a sized type under a handler is reported once, as `E-REF-002` asking for
  a refined type or a test.
- **The integer families.** LR 6.4's table claimed every integer type has three families; only `Int` has them, so
  the table now says so, and the sized families are planned for v0.4.
- **Or-patterns, bare variants, puns, defaults.** R12 is the narrow form. R15's ambiguity is `E-TYP-040`, naming the
  qualified form, and only a comparison's right operand takes the left operand's enum. R9 keeps leading bare names
  positional outside constructors. R13 follows the Language Reference's `Default` interface: `Name.default()`.
- **Map lookups and `@ignorable`.** R11 covers `get` with `String` keys only. `@ignorable` is an aspect, and the
  parentheses of any aspect are now optional.
- **Reassigning a binding that holds a loan.** LR 7.3's "a loan-holding binding cannot be reassigned at all" means
  a binding that holds a loan whole and is a path to the owner: a parameter, `let r = alias p`, `let r = editable p`,
  or a binding that receives a `from` result that is itself a loan; both checkers reject reassigning one. A
  `let mut` binding that receives a loan inside an optional, a tuple or a record (`let mut t = xs.get(0)`) may be
  reassigned, as both checkers and v0.0.1 already allowed: the new value's loans replace the old ones at the
  assignment, and the old value is not destroyed (LR 7.9). So after `t = xs.get(1)` the list stays lent until the
  end of `t`'s block (D-348), and after `t = null` it may change. Loans stay lexical: the assignment replaces the
  value that held the loan, and a loan's last use never ends it. For a tuple or a record that holds a loan, both
  checkers still reject the reassignment, and returning one, although the rule allows both (D-363, a known
  limitation).
- **The migration.** `fortis fmt` rewrites old forms only where the meaning is the same, and checks the result
  before keeping it. A module of a package is rewritten in its package. There is no rewrite for logging,
  `@ignorable` or `derive Default`: each is the author's choice.
- **A string result of a `from` function.** The wording of LR 7.6 that came with D-381's fix called every literal
  a value of the function's own, which contradicted 6.6 (a literal without interpolation is a `StringView from
  static`) and native code, which builds it. The narrower reading is taken (D-386): `StringView from xs => "plain"`
  lends, from static, and is accepted; `"x${…}"` allocates a fresh `String` and is `E-OWN-051`, as is `"plain"`
  where a `String` loan is declared (`alias String from xs`), since the conversion allocates. 7.6 now says so,
  citing 6.6.

## Defects fixed

|---|---|---|
| D-158 | Both checkers rejected a pattern nested inside another (`Next(tail: End(value: _))`, `present(Node(value: b, next: _))`): a nested pattern's fields were looked up in the outer variant, and its bindings were collected twice. | Each variant or class pattern names its own fields only, and its bindings are collected once; nested patterns check and run on every backend, with or without an or-pattern. |
| D-240 | Native code aborted on `Int.MIN % -1`. | Native code computes the language's remainder. |

fallback, which the check of D-373 did not enter; one rule for what a `from` result may be made of replaces the
walk of each shape, and fixes D-377 with it. The ninth candidate's re-check (Kimi K3 on OpenCode, and GLM 5.3)
found D-385, an `or recover` or `catch` whose recovery is the function's own, which that rule did not enter, and
D-386, an interpolated string returned as a view `from` a parameter, which it judged by the text's recorded type;
the rule now enters an outcome expression and judges text by what it is. The wide review of the ninth candidate
found D-391, a deferred block that named a local only inside an interpolation, which the checkers let `return t`
move out: the unmarked `return t` is new in this release, so a program v0.0.1 refused loudly ran wrong silently on
two backends; the checkers now read a deferred block's interpolation holes for the places they name, and the VM
and the interpreter stop loudly where such a check is missed. The wide review also found the
documentation's stale claims, corrected here: two known-limitations rows that no longer reproduced, on v0.0.1
either (D-52.9, D-55.11), a clause each of D-344's and D-360's that native code handles, the rustc code D-156's
row cited, the guide's claim that every integer type has the named operations (only `Int` has them), the pages
that taught v0.1, v0.2 and v0.3 material without a preview marking, the agent mode's missing row for
`E-NAM-034`, and a test record it showed without the `line` that `fortisc test` now writes. The tenth candidate's
re-check found D-411 and D-412 in the fixes themselves, fixed in place for the eleventh candidate, the release.

### Programs now rejected

Some programs that the earlier checkers accepted were unsound, and are now rejected. Each has a sound form.

- A `let` pattern that can fail to match (D-243): `let End(value: a) = move c` is `E-MAT-004`. Write a `match`
  that handles the other cases.
- A loan where an owned value is expected (D-341). `func first(xs: List[Item]) Item? { return xs.get(0) }` is
  `E-OWN-001`, because `get` lends the list's element. Bind the loan and copy it, `let v = xs.get(0)` then
  `return copy v`, or match it, `match xs.get(0) { present(w) => copy w ... }`. A value that cannot be copied (a
  `Shared`, a class holding a capability) is `E-OWN-002`: keep the loan, or take the value out of its owner. The
  same holds for a `??` whose result can be a loan: `return s ?? fallback` with `s` a read parameter is written
  `return copy s ?? fallback`.
- An error whose `message` names a field its payload does not have (`message: "late ${hour}"` with no `hour`) is
  `E-NAM-001`: the rendered message would show it unfilled. Name a payload field, or add it to the payload.
- A class whose derived default contains itself (D-335, D-336): `class Node derive Default { next: Node }` is
  `E-TYP-090`. Make the field optional (`next: Node?`) or give it an initialiser.
- A change to an owner while a binding holds a loan of its element (D-348): after `let t = xs.get(0)`,
  `xs.pop()`, `xs.push(…)` or `xs.set(…)` is `E-OWN-010` and `move xs` is `E-OWN-011` until `t`'s block ends,
  after `t`'s last use too, since loans are lexical (LR 7.3). The same holds for `xs.first()`, `m.get(k)`, a
  cursor's item and a tuple, record or `??` that holds the loan. Close a block around the loan, or `copy` what it
  lends, before changing the owner. Native code already refused these programs when the loan is used after the
  change; when its last use comes first, every backend ran them.
- A value of the function's own returned where the result is declared `from` a parameter (D-373, D-377, D-381,
  D-385, D-386): `func pick(xs: List[Token], d: owned Token) alias Token from xs { return xs.get(0) ?? move d }` is
  `E-OWN-051`, because the caller would hold a loan of a value that ended with the call. A `from` result is a loan,
  so what produces it must lend: a place read through a loan, `alias p`, a call whose result lends, a `??` both of
  whose sides lend, an `if` or `match` every one of whose results lends, an `or recover` or `catch` whose value
  side and every `recover` lend, `present` of one, or, where the result is a view, a literal without
  interpolation, which is a view of static storage (`StringView from xs => "plain"` is accepted). Anything the
  function constructs is rejected: `return move d`, a copy, a fresh value, an interpolated string (`StringView from
  xs { return "count ${xs.count()}" }` allocates a `String`), a literal where a `String` loan is declared (`alias
  String from xs => "plain"` converts by allocating), a tuple or record literal (`return (xs.get(0) ?? move d, 1)`),
  a constructor, a lambda, a call whose result is owned, and a `??`, `if`, `match`, `or recover` or `catch` any of
  whose results is one of these (`null => move d`, `or recover move d`, `recover move d` in the handler), at any
  depth; a trivial value holds nothing and is exempt. Bind the loan and return an owned value from a function
  returning `Token`, `let v = xs.get(0)` then `return copy v ?? move d`, or lend on every path; a value that cannot
  be copied is taken out of its owner, or the caller keeps the fallback. The interpreter and the VM ran such a
  program without the fallback's `cleanup`, or the VM alone did for a tuple, a record or a recovery; native code
  refused it.
- A deferred block that names, only inside a string interpolation, a local the function moves out (D-391):
  `defer { console.print("read ${t.label}") }` followed by `return t`, `return move t` or `eat(move t)` is
  `E-DEF-002`, as the bare `console.print(t.label)` always was, and `defer { discard "${seen.used}" }` where `seen`
  holds a loan of its block is `E-OWN-052`. A name inside a hole is a use of the place (LR 3.6). Read the local in
  the body and keep the deferred block to what stays, or return another value. The interpreter ran such a program
  reading the moved value, the VM stopped the deferred block silently with exit 0, and native code refused it.

## Moving your code

```sh
bin/fortis fmt --write PATH
```

`fortis fmt` now runs the v0.0.2 migrations before laying the code out (`--no-migrate` turns them off). It drops a
`Void` return type, a receiver marker the declaration already shows and the `move` of `return move local`; it moves
`main`'s capabilities into its parameters and drops `export` and an unused `args`; it removes a test's `or fail`
and a map lookup's key copy; and it writes puns, or-patterns, checked operators and bare variants. Each rewrite is
kept only where the program means the same: the module must check before and after, on its own or, for a module of
a package, in its package. A rejected module gets only the syntactic rewrites that leave its records where they
were. The formatter prints how many rewrites it made to each file on standard error.

This repository was migrated that way: the examples, the pilot application, both acceptance applications, the
library and the conformance corpus, and every example of the guide, the agent mode, the README and the
specifications except the Language Reference, which states both forms. A documentation example that demonstrates an
open defect is written in the new forms too, and the defect register records its new text. Fixtures that pin an
older form on purpose keep it.

## Known limitations

[Known limitations](../guide/known-limitations.md) lists the open defects in this release's scope, each with a
workaround ([agent mode](../agent/known-limitations.md)). v0.0.2 adds these to them, in a section of their own:

- The older forms are accepted alongside the new ones. A reader may meet both until code is migrated.
- `fortis fmt` does not rewrite a logging call, add `@ignorable` or `derive Default`, or rewrite a `main` that
  reads its `Capabilities` record other than field by field (a capability inside an interpolation, or the record
  moved whole). Those are left to the author.
- `fortis fmt` never rewrites `Int.shiftLeft(a, b) or fail` to `a << b or fail`, although the two are the same
  operation (D-404), and it keeps a `pure` or `noalloc` written on a lambda, although the function type the lambda
  is passed to already states it (D-406). Both are cosmetic: write the shorter form by hand.
- The Language Reference's own example of an exclusive loan returned `from` a parameter (LR 7.6, `editable Cell
  from c` returning `editable c`), like any returned exclusive loan, does not build natively; the interpreter and
  the VM run it (D-185, there since v0.0.1 and recorded for v0.1; now on the known-limitations page).
- Checked operators cover `Int` only. The sized integer types have no checked, wrapping or saturating operations
  yet (planned for v0.4), so an unproved operator on one needs a refined type or a test.
- A module of a package is not given its inferred facts back by the formatter unless it checks on its own.

The fourth, fifth and seventh candidates' re-checks, and the work on D-348 and D-366, found defects that v0.0.1
already had. Under the rule that a release is no worse than the last (X-416) they are recorded for v0.1, each with
a reproduction, and the known-limitations page lists them in a section of their own, "Defects carried from
v0.0.1", with the shape to avoid: a generic body is not checked for a loan made owned (D-352); a loan given out of
an `if` or `match` branch, or lent by a `match`'s temporary scrutinee, ends too early (D-355); a field read through
an optional loan with `?.` is typed as owned (D-356); an owned place written without a marker on the left of a `??`
whose result is owned is accepted, so two bindings own one value (D-357: write `move some ?? fallback`); a loan held
inside an optional is treated as ended after a loop that may skip the statement ending it (D-362); a `defer` may
read a binding of its block that holds a loan inside an optional (D-364); a binding of a `??` whose fallback it owns
can be copied into a binding that outlives it (D-369), and the interpreter runs that fallback's `cleanup` when an
unmarked copy of the binding ends (D-370); a `??` whose fallback is the statement's own, lent to a read parameter,
is never destroyed on the interpreter or the VM (D-375); the interpreter loses a record field's old value's
`cleanup` when the field is assigned (D-376); a `fn once` closure may return a loan `from` a `move` capture that
the consuming call destroys (D-379); a tuple built around a value of the function's own, bound first and returned
inside `present` as a `from` result, passes both checkers, and the interpreter destroys the value at the call while
the VM never does (D-388); and an `if` nested in an arm of a returned `match`, giving a loan on one branch and the
function's own value on the other, passes both checkers, and both running backends destroy the value at the call
(D-389); a loan of a call's temporary receiver (`fresh().get(0)`) outlives the temporary (D-392); a `pure` function
prints through the `cleanup` of a value it drops (D-393); a lent `match` payload is destroyed at the arm's end on
the interpreter, and for a plain optional on the VM (D-394); and a `from` result given out of an `if` or produced
by an expression body may lend the wrong parameter (D-395). Avoid those shapes: the checkers accept them. Native code does not yet build a function whose result is
an optional loan of text (D-353), or that unmarked `??` when its left side is null (D-354), or a generic function
whose result is an optional loan of its type parameter instantiated at a class (D-387), or a byte string as a
`BytesView from xs` result and an `if` giving a string literal beside a view through a loan (D-390), or the
bind-first spelling of a bearing aggregate `from` result (`let t = (xs.get(0) ?? move d, 1)` then `return t`), so
such a result has no spelling native code builds yet (D-360); and the interpreter stops on a marker written on a
call of a module function (`alias first(alias xs)`, where the marker belongs on the argument alone), which the VM
and native code run (D-382). Native code does not build `first()` on a list of a class (D-396), nor an anonymous
record returned past a deferred block that reads it, whatever its fields (D-415, found by the fixture of D-411), and
every backend refuses `Array.filled` sized by its expected type (D-399); I/O through a local's capability field is refused by the
VM and mislabelled an internal defect natively (D-397); a binding that holds a loan is charged the lent type's
`cleanup` effects (D-400); a `let mut` cursor cannot be reassigned (D-401); and after `match move o` of a binding
that holds a loan the owner stays frozen, a limit of this release's loan holders (D-402). Each is on the
known-limitations page. The new loan rules also reject two valid programs: a tuple that holds a loan cannot yet be
reassigned or returned (D-363), and a `defer` cannot change a list while its block holds a loan from it inside an
optional (D-365). All four are on the known-limitations page.

## How it was checked

- The release workflow passes at the release's tag: the gate's full tier with every step, cargo test in release
  and debug, the determinism check (the compiler from two clean clones, and native programs built twice, byte for
  byte) and a secrets scan.
- The three backends agree on every conformance program, and every documentation example is checked by both
  checkers and run on the interpreter, the VM and native.
- Every change was reviewed, and each of the three implementation streams passed the full gate before merging.
- Six release candidates. The first had a review of each implementation stream by Codex and a whole-release review
  by Codex and Grok; Codex's review of the expressions stream was blocked by its provider's content filter, so Grok
  reviewed that area. Each later candidate had a re-check by Codex and Grok that re-ran every earlier reproduction.
  The re-checks of the second, third and fourth candidates found blocking defects, each fixed before the next
  candidate. At the fifth, Codex was blocked by the same filter twice, so Grok ran the re-check and then a second
  pass on the runtime changes, which found D-366 and D-367 in the fourth candidate's own fixes. The fifth
  candidate's release run also failed in one debug-build test, whose thread was too small for the checker; the
  sixth candidate fixed the test, and the seventh fixed D-366, D-367 and D-368. The seventh candidate's re-check,
  by Codex and Grok, found D-372 and D-373 in those fixes and the loan rules, and D-374, which v0.0.1 also had; the
  eighth candidate fixed them, and D-378, which the fix's own sweep found. The eighth candidate's re-check (Codex
  alone: Grok's usage balance was exhausted) found D-381, the tuple-shaped neighbour of D-373. Rather than fix one
  more shape, the ninth candidate replaces the shape-by-shape rule with a structural one: a `from` result must be
  made of an expression that lends. Its re-check ran on OpenCode, with Kimi K3 and GLM 5.3 through Fireworks, two
  model families; it found one branch the rule had missed (D-385, an owned recovery value) and two shapes that evade
  it, which v0.0.1 also accepted and which are recorded (D-388, D-389). Rather than another narrow round, one wide
  review of the ninth candidate then ran, by scope, on four OpenCode runs: the loan and `cleanup` rules as a matrix,
  the seventeen reading changes and the formatter, and the release as a whole against its documents. They found one defect this release introduced (D-391, a `defer`
  that names a local only inside an interpolation, which R16's unmarked `return` then moves), eleven that v0.0.1 also
  had, recorded for v0.1, four cosmetic gaps in the formatter's rewrites, recorded as limits of this release, and
  fourteen stale or missing statements in the documentation, corrected.
  The tenth candidate fixes everything those reviews found that this release introduced or made worse, and its own
  re-check covered those fixes alone, on Kimi K3 and GLM 5.3: every fix held, and both reviewers found the same two
  defects in the fixes themselves (D-411, the interpreter's new rule for a returned local not knowing a `trivial
  class`; D-412, an escaped `\${` misread as an interpolation), fixed in place for the eleventh candidate, with no
  further review round. The release is the eleventh candidate.

This release makes no performance claims. Performance is judged at v1.0.
