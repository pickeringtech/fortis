Fortis v0.1.0: Model a domain#

Released 31 October 2026 by Pickering Technologies Ltd, under the MIT License (LICENSE).

v0.1 lets you model a domain. Give a quantity a range, give money its own type, describe a service through an interface, and put validation where a value enters the model. Conversions, text operations and collections make that model usable in an ordinary program. Ownership, failure handling and the capabilities a function needs remain visible and checked.

The coffee-shop showcase is the complete program: it reads orders, rejects bad input, prices the accepted drinks and prints a receipt. The worked example explains each part. Both checkers judge it, and the interpreter, VM and native backend run its main and tests with the same expected output.

Before and after#

This v0.0.2 program parses a size by hand and checks a quantity at the point of use:

Fortis
// illustrative: v0.0.2
import fortis.host { Console }
enum Size derive Displayable {
  Small
  Medium
  Large
}
error BadOrder {
  code: "order.invalid"
}

try func parseSize(text: StringView) Size {
  if text == "small" { return Small }
  if text == "medium" { return Medium }
  if text == "large" { return Large }
  fail BadOrder()
}

try func order(size: StringView, quantity: Int) String {
  if quantity < 1 || quantity > 9 { fail BadOrder() }
  let parsed = parseSize(size) or fail
  return "${parsed}: ${quantity}"
}

try func main(console: Console) {
  console.print(order("medium", 2) or fail)
}

The same program in v0.1 gives the accepted order a type. The enum declares its text conversion; the quantity carries the range that every later use can rely on:

Fortis
// illustrative: v0.1.0
import fortis.host { Console }
enum Size derive Displayable, convert from String {
  Small
  Medium
  Large
}
type Quantity = Int<1..9>
class Drink {
  size: Size
  quantity: Quantity
}

try func order(size: StringView, quantity: Int) String {
  let drink = Drink(size: size as Size or fail, quantity: quantity as Quantity or fail)
  return "${drink.size}: ${drink.quantity}"
}

try func main(console: Console) {
  console.print(order("medium", 2) or fail)
}

Both print Medium: 2. A bad quantity is an outcome at the conversion, and a Drink cannot hold an unchecked quantity. The showcase extends this to a declared try convert from String(line) member, so a literal such as "medium, 1" as Drink follows the same validation as a string or a trimmed view (LR 6.13).

Moving your code#

The older forms remain accepted. fortis fmt --write PATH resolves each rewrite by declaration identity and keeps grouping and evaluation order:

Older formDocumented form
From[S], T.from(x) and x.to()x as T; to() needs a written expected target before it can be rewritten
derive From[S]derive convert from S
String.from(view)view as String; an existing owned string is copied where the old call copied it
T.validate(x)x as T; a proved conversion is wrapped in Outcome.success when its consumer needs an outcome
A handler directly on proved validationThe plain value or conversion, once the formatter proves the handler unreachable

A borrowed operand still needs its copy. A fresh owned string does not acquire an extra immediately invoked copying function. Unknown operand types and unwritten to() targets stay in their older form with a note. Generic legacy From implementations remain accepted. The formatter does not invent conversion members, rewrite a hand-written parser as enum derivation, or remove explicitly written lambda captures and modifiers. The v0.0.2 migrations also remain available.

Decisions for review#

These are the integrator's readings made during v0.1, including later corrections to earlier stream decisions. The owner can review them before release. Register identifiers identify the internal decision record; the linked Language Reference is the public rule.

  • Refinements and newtypes (X-510 to X-512, X-514). Only the bases and measures listed in LR 6.3 refine; counts start at zero and bounds lie within the base. Newtype constructors require a proved representation. Newtypes inherit the four comparison, hashing and display interfaces whenever the representation does, including non-trivial representations. Mutable collection type arguments remain invariant; an inner refinement must be proved.
  • Structural values and narrowing (X-685 to X-688). Optionals follow their values' subtyping, so a refined optional can widen; other containers remain invariant. Tuples need equal arity, and anonymous records need the same field names, matched by name without width subtyping. Corresponding values follow ordinary assignability. Parentheses preserve comparison and conjunction facts, with effects checked once in order. Branches of one integer base join by the hull of their intervals; different bases gain no conversion.
  • Canonical text and length-refined reads (X-690, X-691). Numeric parsing consumes the whole canonical ASCII input without trimming, exponents, separators or suffixes. An integer beyond the target range remains conversion.out_of_range; beyond the signed 128-bit carrier its payload keeps the exact text. Decimal coefficient or scale overflow remains conversion.parse. Float, Float32, BigInt and direct parse-and-refine conversions remain absent from the table. Length-refined collections retain their base's reading operations and type arguments. A static index must be below the guaranteed minimum length, or proved below the actual length; the maximum alone proves no element exists. Mutation remains E-REF-003, and refined views retain their loans and result origins.
  • Captured loans, linear copying and native closures (X-695 to X-698). Captured loan origins survive annotations, generic calls, aggregates and branches. Every owner must outlive the closure and its local holders; collections, class fields, enum payloads and newtypes cannot store these loans. Moving a loan-carrying closure preserves its origins; capturing an owned value by move or copy introduces none. Owned callback arguments name their region, including inside aggregates. Linearity excludes Copyable before structural rules and bounds, including Must. A returned loan of T needs no linear bound because it does not hold T by value. Child loans retain their parent relationship and root owner, permitting their own access while parents and conflicting siblings remain restricted. Native generic holders retain concrete callable environments without boxing, and returned owned callbacks carry their region's lifetime bound. Concrete callable fields remain D-685.
  • Inference and native bounds (X-513, X-515, X-516). A generic T is ownership-bearing in its body. The implementation applies a written expected type before checking arguments, allowing heterogeneous values to be boxed as they are built; arguments supply parameters the expected type does not fix. This is the recorded reading of the plan's arguments-first wording. Unannotated inferred integer arguments widen to their base. Native bounds follow the signature; derived ordering is lexicographic, and hashing uses the declared equality and hash methods.
  • Range patterns (X-517, X-518, X-523). Patterns apply to integers, including refinements, but do not unwrap newtypes. Bounds are resolved constants, folded without changing evaluation. Coverage combines unguarded ranges only over a refined scrutinee; literal arms do not contribute intervals, and an unrefined integer still needs otherwise. Narrowing uses the interval hull or residual endpoints the checker can prove.
  • Interfaces, mixins and contracts (R7 to R12, X-476, X-478). Dynamic uses need eligible interfaces and the required implementation chain. Mixins are checked in every applying class while retaining lexical names; private access to a required method belongs only to that mixin body. implement targets exclude newtypes and generic classes or enums. Self anywhere outside the receiver makes an interface ineligible for dynamic use; associated functions and constants do not count as dynamic members. Bounds are checked at the implementation and at use; associated constants must have the interface's declared type. A contract's capability clause must name an authority, and contradictions are checked within a contract and across a function's modifiers and contracts. The owner replaced mixin requires Interface with required method signatures (X-525, X-526); the former is rejected and has no automatic rewrite. Contracts expand the existing modifiers and cannot demand and forbid the same effect.
  • Cleanup and loan holders (X-477, X-495, X-496). Owned parameters carry their fields' authorities for destruction. Every destroyed temporary contributes cleanup effects; a loan does not. A selected owned recovery replacement is destroyed at its actual lifetime. Owned cursor bindings may be reassigned; the old cursor ends and its loans are replaced, while a binding that is itself a loan cannot be reassigned.
  • Conversions (X-550 to X-555). Targets are named types. Conversions never search through a third type or round implicitly. A declared pair belongs in a source or target class or enum, with ordinary visibility, effects and ownership. Generic handwritten members and newtype members remain excluded. Newtype wrapping is total when proved, otherwise fallible; unwrapping is one step within the declaring module and retains refinements. Linear representations require proof before wrapping. Explicit field-wise derivation is total, borrowed and copies eligible fields in declaration order. Legacy generic implementations keep their existing allowance.
  • Migration (X-542, X-544, X-677). The grammar determines grouping. Proof requires a known operand type. A stored validation outcome retains its shape, while an immediately handled proved success can lose its handler. Copies are retained for loans and omitted for a fresh owned string. Each rewrite evaluates its operand once.
  • Collection callbacks and helpers (X-565 to X-571, X-573, X-579). tryEach, tryMap and tryFold take callbacks returning outcomes, stopping at the first failure in element order. fold reads its accumulator and takes the next one from the callback. each takes an editable fn mut and visits in order. Searches lend elements; operations returning copies require Copyable. take and skip clamp their counts, chunked requires a positive size, zip stops at the shorter list, and sortedBy is stable with one key call per item. Optional and outcome map are the only new wrapper helpers; existing operators handle the other cases.
  • Maps, sets, queues and arrays (X-569, X-575 to X-578, X-615). Maps and sets keep insertion order and read text keys as views. for is their available traversal, without a cursor method. One Deque serves both ends; it uses two lists and transfers items when rebalancing. SortedSet keeps a sorted list, with binary lookup and linear moves on updates; range queries exclude the upper bound. fromList consumes, toList copies. Arrays expose functional methods through asView(). Key requirements apply to written and inferred instantiations by type identity, and Hashable grants its required Equatable interface.
  • Lambda captures and collection newtypes (X-580, X-581). Parentheses preserve a directly loaned lambda's eligibility for inference. A written kind or capture list opts out; repeated places share a capture, and distinct field paths stay distinct. Forwarding reaches one collection representation, including a refinement, but does not add fields, indexing or associated functions or unwrap another newtype.
  • Text (X-595 to X-598). Search positions count scalars. Splits and lines own their strings; trimming lends a view. Whitespace follows Unicode White_Space; lines end at LF or CRLF, with no extra empty final line. Empty search text matches at zero, but an empty split separator or replacement pattern occurs nowhere. Case operations are explicitly ASCII. String.join takes a list view of owned strings. Carriage-return and NUL escapes agree across backends, and Text.words uses the same whitespace definition. Both library reference modes are generated from declarations, comments and effect rows, and the gate checks their freshness.
  • Stored loans and temporary views (X-605, X-625). Owned storage cannot hide a non-static loan in a generic argument or callback result. A literal does not make an ordinary StringView element type static. A stored view of any possibly owned temporary branch is refused; bind the possible owner first. Same-statement reads remain legal.
  • Callback effects and linear traversal (X-519 to X-522, X-610, X-611, X-620 to X-622). The callback type's permitted effects reach the caller; pure fn can allocate and only pure noalloc fn excludes allocation. Generic classes and enums declare linear bounds before the body, and that clause accepts only linear bounds. A bound governs the body that declares it; a caller's bound cannot supply a missing callee bound. Returning a type parameter by value or receiving it from a callback needs the bound too. Owned parameter obligations must be discharged at explicit returns, fall-through and expression bodies. List.clear() destroys non-linear elements without allocation; linear elements use consuming operations instead. A consuming loop must discharge every item on every path and cannot abandon its hidden remainder, including through unwind or cancellation. A callback's local return belongs to its own activation. Read-self traversal keeps obligations with the owner, even if the receiver is written with move; a fresh borrowed linear owner is refused. consumeEach runs to completion and has no effect exemption. Non-failing map and flatMap preserve linear results; tryMap rejects them, and Outcome.map and collect reject linear input payloads. A linear user cursor needs a terminal consuming operation not supplied by the current interface, so it is refused; a bounded class can transfer its contents into a standard collection and consume that. Non-linear user cursors run on all backends, with both consume and next contributing effects.
  • Enum parsing and optional methods (X-631 to X-634). Enum parsing supplies two exact text pairs, compares whole names with ASCII case folding, neither trims nor generates a reverse conversion, and rejects ambiguous names. Its failure owns both input text and variant names. Optional calls accept read, non-try methods, skip arguments on null, flatten optional results and retain effects and loan provenance. A conversion ending in an owned result ends its source loan; one returning a view retains it.
  • Names and diagnostics (X-640, D-665). The prelude supplies fallback names; a local type can shadow one, while an explicit braced import cannot collide with a local declaration. Identity includes the declaring module and package throughout nested types and bounds. A diagnostic qualifies colliding spellings by module, and by package version when the module name also collides.
  • Void and declared text members (X-675, X-676). Void has its one value but no constructor; Void() is E-TYP-040, with an empty block lambda or a function returning nothing as the correction. A declared conversion from String or StringView accepts both text sources. Read parameters borrow without allocation; owned String copies a view or literal and records allocation. Existing strings still obey the written ownership mode, and competing text members remain E-TYP-182.
  • Native values (X-590 to X-594). Replacing an owned value preserves its destruction duty. A Never fallback keeps the surviving branch's loan. Expected numeric types reach give and recover, and native integer widths preserve every accepted interval. Generated names cannot collide with Rust's built-in spellings. Callback parameter modes survive lowering, including owned arguments. A selected text loan passes through coalescing or recovery without a temporary owner; a genuinely owned receiver ends at the full statement.
  • Testing and output (R13, X-541, X-645, X-646, X-655). expect belongs to test, property and cases bodies; there is no separate test-only module category. Emit-only builds create a crate and no executable. The showcase pins output and tests on every backend; VM --stdout separates literal console output from its diagnostic envelope. Shared unit cases now sit below corpus execution in the gate. The pilot rebuild at the candidate remains part of the release check.
  • Parser timing (X-678, applying X-149). Parser acceptance, tree and ambiguity agreement always decide the gate. Timing remains measured and recorded; FORTIS_PARSER_TIMING=1 judges the 50 ms budget for the quiet-machine v1.0 release check. A performance number alone does not fail a v0.1 gate (D-670).

Release-candidate fixes#

These readings were made while fixing the release candidate's defects.

  • Async function values (X-736). A function value and its receiving type must agree on async status wherever a function type is written: a binding, argument, return, field, generic argument or qualified import. Declare the function async, or wrap its call in an async lambda. The reverse rejection and the try rules stay unchanged; no backend execution changes. Three older routes are not covered yet and are carried to v0.2 (D-754 to D-756).
  • Function results and array constructors (X-734, X-735). Named function values retain their success result and effect modifiers, like lambdas. Calls apply each implied Outcome or Future wrapper once. Array sizes are resolved at the constructor type reference, including postfix chains and interpolation holes, using ordinary integer literal spellings.
  • Optional arguments, arrays, records and loans (X-730 to X-733). The optional argument boundary covers all ways to consume an existing obligation, while a closure body has its own activation. Return handling means catch with return, the supported syntax; this adds no or return form. Array sizes come from resolved types and use the ordinary integer spellings. Native record keys include field representation types recursively, erasing refinements and ignoring field order. An editable local loan keeps permission to edit its referent without permission to reassign its binding.
  • X-710: reject moves of existing linear places anywhere in an optional argument, including nested calls and captures. Arguments constructed directly without moving an existing place remain permitted.
  • X-711: List index places use the same element expectation as set. LR 7.2 now names the existing List and FixedList literal-index forms alongside Array; variable-index places remain excluded.
  • X-712: editable structural loans preserve nested member types. Read loans, moves and copies retain value widening.
  • X-713: an invalidated refinement at a function argument uses LR 6.3's E-REF-001. E-REF-002 remains the arithmetic and indexing diagnostic. Binding-with-subpattern is outside v1; a separately bound scalar copy tests the same fact-retention rule.
  • X-714: release only the operand loans of an expression whose known result cannot carry them. Keep loans belonging to other enclosing operands and any result that can still lend.
  • Formatter fix round. LR 6.13 already requires a copy for an owned string place, including a written move or alias; no language rule changes. Canonical guide checks cover accepted and rejected programs in their package context, excluding illustrative fragments and deliberate syntax errors, which cannot be formatted.
  • Runtime fix round (X-715 to X-719). A callback failure names its lambda source label; propagation does not replace that origin. Array sizes are resolved per expression and captured by constructor values. Grapheme properties are pinned to Unicode 15.1, generated with Python 3.12's Unicode 15.0 categories plus official property differences; the promised control, prepend, Indic and ZWJ rules apply, while Hangul GB6-GB8 remain unimplemented. Commands retain one input snapshot. Optional aggregate injection, editable record writes and qualified module calls implement existing rules.
  • Function values (X-725 to X-729). A named function expression, including an unannotated binding, has its declared signature. Existing marked declaration references retain that signature. Written owner arguments or a complete expected function type specialise generic values. Any remaining unresolved parameters are E-TYP-040; wrap a typed lambda or call directly. A generic derived default value requires written owner arguments. Bounds stay checked at direct calls. Instance methods, including forwarded newtype methods and interface or type-parameter methods, require a call or a lambda with captures. A payload variant without a call needs a complete expected function type, including its type arguments. Bare class and newtype names remain rejected as constructor values; wrap their constructor calls.
  • Optional collection lookup (D-721). A null element and a missing index both produce null; a present element lends its payload, with trivial values copied as usual.
  • Tree dump comparison (D-727). An escaped zero-width joiner and the same literal scalar represent the same token. Agreement compares decoded token values, token kinds, tree structure and source positions; malformed dumps still fail.

Defects fixed during the release candidate#

The review of rc.1 and a re-check of its fixes found these defects, and a sweep of every function-value form found D-737 to D-741. Each fix is checked on both checkers and, for running programs, on all three backends.

Checkers#

  • D-749: both checkers reject a synchronous callable converted to async fn or async try fn with E-TYP-040, asking for an async declaration or lambda. The async forms run with the body deferred on every backend. Three routes that v0.0.2 already had remain open (D-754 to D-756, under Known limitations).
  • D-667: returning retired text validation releases the copied source's loan.
  • D-705: optional call arguments cannot move a linear obligation on a path that may skip the call.
  • D-706: List index assignments check the declared element type, including refinements and optional elements.
  • D-707: editable records and tuples compare their member types invariantly; read loans and owned values still widen.
  • D-708: range-pattern facts precede guard evaluation, so a guard's writes and editable loans invalidate them.
  • D-709: a returned scalar count of a trimmed view retains no source loan; a returned view still lends.
  • D-720: comparing trimmed views returns a Bool without retaining operand loans.
  • D-725 and D-726: associated function values substitute written type arguments into parameters and results; qualified module function values carry their declared signatures and are bound without an eager call.
  • D-737 and D-738: unspecialised generic functions and forwarded newtype methods cannot escape as untyped values. Both checkers give E-TYP-040 and ask for a direct call or a typed lambda.
  • D-739: payload variant values need an expected function type; bare constructor functions now run on every backend.
  • D-741: binding a named function creates its non-capturing value without requiring a local ownership marker.
  • D-742: both checkers reject handling or passing an existing obligation inside an optional-call argument, including nested handlers and chains. Fresh obligations created and handled inside the argument remain legal.
  • D-746: calls through named try and async function values apply their result wrappers once and retain their effects; direct calls and local bindings run on every backend, and both checkers reject a second outcome match against an Int. Native boundary limitations are recorded in D-751.

  • D-714: piped source is retained through checking, testing and execution, so rejected programs and failing tests stay failures.

Formatter, documentation and tools#

  • D-710: known-limitations pages now reflect re-run reproductions, with fixed sub-items recorded separately.
  • D-719: formatting String.from(move s) keeps the copy and its allocation effect. Both checkers still reject a noalloc caller, and the conversion goldens run before and after on all three backends.
  • D-727: checker agreement compares decoded token text, preserving structure and positions while allowing equivalent Unicode quote spellings in tree dumps.
  • D-730: the coffee showcase and its pinned guide copy are formatted. The formatter gate now requires shipped examples, the ledger pilot and guide programs to be canonical, with migrations enabled.

Known limitations#

The generated known limitations lists every open non-blocking defect in the release's scope and its workaround, with an agent version. This includes the remaining native generic and closure shapes (D-55), checker refusals (D-251), heterogeneous closure returns (D-270), optional test comparisons (D-342), mixed loans and owned values (D-360, D-361), test failure origins (D-508), Map and Set cursors (D-535), collection update costs (D-543, D-546), generic copyability (D-548), callback parameter modes (D-550), moved generic function values (D-583), structural Hashable bounds (D-590) and optional dynamic injection (D-605). Running a package inside the toolchain checkout from another working directory loses conversion facts on the interpreter (D-668); run it from the checkout root. A callback returning bare Void needs an explicit Outcome[Void] receiving type, or an empty block lambda, for inference (D-669). Rust record-schema validation is permissive (D-640). Native lowering also refuses a concrete work: fn() Int class field (D-685); use a generic Holder[F] instantiated as Holder[fn() Int]. Native generic associated methods whose owner type arguments cannot be inferred from value arguments also fail to build (D-748); use a free function. Nested outcomes are flattened by the interpreter and VM (D-750); return the inner outcome in a record field. Native refuses try fn values across some boundaries (D-751); use a local binding, generic holder or tuple. Direct record-field calls are refused (D-752); bind let f = alias holder.work before calling, using a generic holder for native. Native also refuses ordinary function fields in records (D-753); use a generic holder. Their verified workarounds are on the generated page.

Three defects that v0.0.2 already had are carried to v0.2, and a program can pass both checkers and still go wrong because of them. Both checkers accept an unbounded type parameter where a concrete type is expected, so a generic function can return its argument as any type (D-754). A synchronous method can implement an async interface method (D-755), and a lambda that is async only through a contract is typed async but runs as a synchronous function (D-756); in both, the body runs before await on the interpreter and the VM. The generated page gives their reproductions and how to avoid them.

The ledger pilot's native rebuild still refuses the narrowed optional moved into Posting.amount (D-55.16). Its sample journal and tests run on the interpreter and VM. The formatter repairs preserve their output; this known native refusal is unchanged.

The large numeric-text parser fixture measured a 60.02 ms warm median against its 50 ms budget on the development host (D-671). Its parses and trees agree. This performance measurement is scheduled for the quiet-machine v1.0 check; the full fixture remains in the corpus.

Full Unicode case mapping, the rest of the standard library, effect polymorphism, concurrent execution and the stability promise belong to later releases. Linux x86-64 remains the release's tier-1 platform. Performance is measured but does not decide a release before v1.0. Older spellings can still be encountered until code is formatted.
