# Fortis v0.1 (draft)

Stored loans in collections are rejected (`E-OWN-053`, D-580). An owned collection, `Shared` or a user generic
class or enum cannot store a view or another non-static loan, including through an optional, tuple, record,
outcome or newtype. The check applies to inferred types and generic instantiations too. Use owned elements, for
example `List[String]` and `text as String`. A plain view of a literal is still a view; only an explicit
`from static` loan type is exempt. Local views, cursors and optional loans retain their existing rules (LR 7.7,
X-605). This is the stream K decision for review; the rest of the release notes will follow the other streams.

Written storage types are rejected on their declaration or annotation; inferred ones are rejected where they
are instantiated. This includes storage hidden in a generic body and a generic function value whose storage
arguments are not fixed. Generic class and enum arguments are checked even when unused in a field. Owned
arguments and callback results retain their loans during this check; a generic adapter cannot erase a result
loan whose origin its signature does not name. An unfixed `List.default()` keeps `E-TYP-160`.

The static exception requires a static source (D-584). An annotation, field, call argument or function-type
conversion cannot relabel a non-static loan as static; this is also `E-OWN-053`.

Views of possibly owned statement temporaries are rejected with `E-OWN-051` (X-625, D-562). The check follows
coalescing and conditional branches, recovery, conversions, calls and interpolation even when the joined type
is a loan. Bind the possible owner first, then borrow it. Static text, named places and reads within the same
full statement stay legal; native temporary lifetimes are unchanged. This is a stream K decision for review.

Numeric parsing rejects whitespace on either side, including a final newline (D-655). The interpreter no longer
reads `1.0` followed by a newline as `0.10`. Canonical integers too large for the target fail with
`conversion.out_of_range`; when the integer exceeds signed 128 bits the failure keeps its exact text as `value`
(D-680, X-690, decision for review). Decimal overflow is `conversion.parse`. The conversion table is unchanged:
text has no Float, Float32 or BigInt conversion, and parsing and refinement remain two explicit steps.

Length-refined lists and views support indexing and every reading method, including generic functional methods
(D-656). A static index uses the guaranteed minimum length; an actual-length guard can prove further indexes.
Mutation and editable loans remain rejected, including indexed assignment (D-681, X-691, decision for review).
Refining a view preserves its loan and result-origin requirement on every backend (D-682).
The checker fixes from F1 reject mismatched tuple elements and anonymous record fields (D-635), and duplicate
class constants or collisions between constants, fields and methods (D-639, `E-TYP-070`). Parentheses preserve
comparison and conjunction narrowing (D-637); if-expression and match results join same-base integer intervals
by their hull (D-638). The owner's decision, "Yes, optionals widen", permits `Int<0..3>?` as `Int?` (D-636, X-685).
Collections and other containers remain invariant, including refinements nested in their element types.

Decisions for review (X-686 to X-688): tuples require equal arity; records require exactly the same field names,
matched by name, without width subtyping. Elements use their own assignability rules and must prove nested
refinements. Parentheses preserve the existing narrowing and effect rules. Branch hulls add no conversion
between different integer bases.

Known limitation found by F1: native builds refuse an anonymous record returned with the same fields in a
different order (D-675, `E-INT-002`); the interpreter and VM run it. Keep the field order consistent for a native
build. Diagnostic record validation D-640 remains open.

F3 closes the captured-loan escape (D-645) and linear copying (D-649) in both checkers. A closure's captured
origins survive generic calls, annotations and branches. Collections, class fields, enum payloads and newtype
representations cannot store a closure that borrows an owner; neither it nor a local aggregate or outcome holding it may escape that owner. Closures
that capture owned values by move or copy can still be stored and returned. Copying Must, Outcome, a linear
type parameter or an aggregate containing a linear value is rejected with E-OWN-002.

F3 also fixes two false rejections: a generic function may return a loan of a linear argument without holding
it by value (D-646), and a child loan of an editable parent remains readable (D-647).

Decisions for review (X-695 to X-697): capture origins are value provenance, distinct from a callable's declared
region; local loan-carrying holders are allowed while their owners live. Moving an already loan-carrying closure
preserves its loans. Owned callback arguments must name their region, including callbacks
inside aggregate arguments, as LR 8.3 requires.
Linearity takes precedence over structural Copyable rules and bounds, and Must is named
explicitly in LR 6.11. A child keeps its parent relationship separately from the root owner, so it remains usable
without permitting conflicting access through a parent or sibling.

Native lowering now returns concrete closures inside collections and generic holders without boxing, and gives
an owned callback the lifetime bound required by its returned region (D-686, X-698, decision for review).

Known limitation found by F3: native lowering refuses a concrete field declared `work: fn() Int` with E-INT-002
(D-685); both checkers accept it and the interpreter and VM run it. Use `class Holder[F] { work: F }` and
`Holder[fn() Int]` instead. The positive F3 fixture runs that form on all three backends, with no boxed closures.
