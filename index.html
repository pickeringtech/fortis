Fortis is a statically checked, compiled language for software written mostly by AI agents. People can read, review and trust it because every decision is written in the source. Ownership, changes, failures and effects are explicit.

  1. 1Checked purityL7

    pure rules out effects such as I/O and clock access. The checker verifies it.

  2. 2Declared failureL7

    try declares that mean can fail. Its caller must handle the outcome.

  3. 3Bounded inputL7

    Int<0..1000> carries a range. ListView gives read-only access.

  4. 4Visible propagationL14

    total + r is checked: an overflow is a failure, and or fail passes it to the caller.

  5. 5Changes declared onceL20–21

    let mut says that readings will change, so the push that changes it needs no other marker.

  6. 6Caller’s recoveryL22–24

    catch handles the failure, reports it and recovers with 0.

  7. 7Authority as a parameterL19, 26

    main declares the console it needs, and the runtime supplies it. Printing uses that capability.

Try this program locally.

Start with a checkout of the Fortis repository. You need Python 3 and a Rust toolchain with cargo. Run these commands from the repository root.

  1. Build the tools

    The reference toolchain uses Python. Build the production compiler with Cargo.

    cargo build --release --manifest-path compiler/Cargo.toml

  2. Save the example

    Copy the complete program above and save it as mean.ft in the repository root.

    The copy includes only the source, without line numbers or annotations.

  3. Check and run

    Check the source, then run it on the reference interpreter.

    bin/fortis check mean.ft
bin/fortis run mean.ft
    Outputbin/fortis run mean.ft
    mean of 4 readings: 25

What a reviewer can check.

Fortis puts ownership, failure handling and authority in the file or diff you are reading.

Who owns a value

Every value has one owner. Loans and moves are checked. Cleanup runs exactly once, at a visible point.

Who handles a failure

A call that can fail says so. Each failure must be handled, reported or passed up. The compiler checks this.

What a function can do

The checker verifies pure. Output needs a console capability obtained from the host.

One program. Three backends.

The interpreter, development VM and native backend must agree on program output. The test suite checks that agreement.

Reference interpreter

The reference for what a program means.

bin/fortis run mean.ft

Development VM

Run with the production compiler's VM.

compiler/target/release/fortisc vm mean.ft

Native executable

Compile through a safe Rust crate.

bin/fortis build mean.ft --out mean

Where Fortis stands.

The latest release is v0.1.0. Each release is a subset with its own documentation and release checks. Performance is judged at v1.0.

  1. v0.0.1Write, check, run, build, format and test programs. Modules, functions, classes, enums, ownership and failures.
  2. v0.0.2Code that says only what matters. Fewer markers, capabilities as parameters and built-in logging.
  3. v0.1.0Latest: Model a domain (v0.1.0). Refinements, newtypes, conversions, interfaces, generics, contracts, text and collections.
See the planned releases through v1.0
  1. v0.2Trust effects and test properly. Checked effects and capabilities, and property tests.
  2. v0.3Build a web service. An HTTP server with health, readiness and metrics built in, SQLite and typed queries.
  3. v0.4Build web apps. HTML, forms, sessions, authentication, Postgres and migrations.
  4. v0.5Run it in production. Telemetry, connection pools, timeouts, rate limits and containers.
  5. v0.6Organise and extend code. Packages with dependencies, checked architecture and extensions.
  6. v0.7–0.9Async, library and scale. Async in your own code, a complete standard library, and tooling for large code bases.
  7. v1.0Stability. Editions, migration and a stability promise. Performance judged against Rust.
